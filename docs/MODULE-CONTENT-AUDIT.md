# QHAZE TECH UNIVERSITY — Module content audit

**Date:** 2026-11-19 · **App:** 0.5.9 · **Course materials:** 1.8.1 · **Scope:** all 328 modules in 82 courses,
3 programmes, 3 academies with programmes, 1 faculty with curriculum (the other 6 faculties and 12 academies have no
courses, so they have no modules). Read-only: no content, data or schema changed.

Per-module results: [content-audit/module-content.csv](content-audit/module-content.csv) (Faculty, Academy,
Programme, Course, Module ID, Module title, Module content status, Lecture content status, Missing sections,
Lectures written), regenerated by `npm run audit:content`.

**No module has its own learning materials.** That includes the 32 modules whose lectures are all written (Lua
Semester 1: LUA101–LUA104 M1–M4; Luau Semester 1: LUAU101–LUAU104 M1–M4). Each of the 11 module sections you listed
is missing in every module: overview and introduction, learning objectives, detailed theory, learning notes, key
concepts and principles, terminology, rules/syntax/formulas, examples and demonstrations, real-world applications,
module summary, references.

Because lectures and modules are now assessed separately, a module is only complete when **both** its own materials
and all of its lectures are complete. By that rule, **no module in the university is complete today.**

## Root cause: there is no module-content feature at all

This is not a set of missing records. Every layer that would carry module materials lacks them:

| Layer | What exists | What is missing |
|---|---|---|
| Curriculum package format (`ModuleDef`) | `title`, `lectures` | any description, objectives or materials |
| Database record (`Module`) | `title`, `description` (one plain text field) | structured sections; the installer leaves `description` **empty for all 328 modules** |
| Course-materials package format (`ContentPackage`) | `glossary`, `lectures` | `modules`: there is no way to deliver module materials |
| Content standard and validator | 24-section lecture standard | a module standard; module validation |
| Application | Library course panel lists each module's title, its lectures and two buttons (Module .md, Module PDF) | a module page; any module text on screen |
| Markdown / PDF / ZIP export of a module | module heading, then the full text of its lectures | module introduction, notes, examples, summary, references |
| Course export | course description, then each module heading and its lectures | module materials between the heading and the lectures |
| Content audit (before today) | lecture-level checks | module-level checks (added now) |

So the module "page" you see is a heading over a lecture list, and the module PDF is the lectures stitched together.
The fix needs a module-content feature first. Writing records alone would not help, because nothing could store,
show or export them.

## Proposed solution

### 1. A module content standard (bilingual, adapted to the discipline)

Each module gets its own materials, separate from its lectures: a coherent overview that ties the lectures together,
not a copy of them.

| Module section | Your requirement | Notes |
|---|---|---|
| module_overview | overview and introduction | what the module covers, why, and how its lectures connect |
| learning_objectives | learning objectives | module-level outcomes (broader than any single lecture) |
| detailed_theory | detailed theoretical explanations | the module's big ideas as one narrative, ≥150 words per language |
| learning_notes | complete learning notes | structured revision notes for the whole module |
| key_concepts | key concepts and principles | the principles the lectures build on |
| terminology | terminology and definitions | glossary links (Click-to-Learn), reusing existing terms |
| rules_and_syntax | rules, syntax or formulas | discipline profile: syntax for programming, formulas for maths, workflows for design; may be marked "not applicable" with a reason |
| worked_examples | practical examples and demonstrations | for programming: new, verified code (no duplicate of any lecture example); for maths: worked solutions; for design: tool walk-throughs |
| applications | real-world applications | industry and real projects |
| lecture_guide | (connects module and lectures) | generated from the structure: each lecture, its role in the module, its status |
| module_summary | module summary | key points and a self-check |
| references | references and learning resources | ≥3 links |

### 2. Storage without a database schema change

Store module materials on the existing module record, as **`Module.sections`** plus a content version, exactly as
lecture materials are stored on `Lecture.sections` today. Neither field is indexed, so:

- the IndexedDB schema (tables and indexes) does **not** change and needs no migration;
- backups, restore and the integrity check already copy whole records, so they carry the new field automatically;
- the existing `description` field is left as it is.

This does extend the data model (the record type gains two optional fields), so it needs your explicit approval. The
alternative (a new table) would be a schema change and is not proposed.

### 3. Delivery through the existing course-materials package

`ContentPackage` gains `modules`, addressed by course code and module number. They are installed by the same safe
installer: validate, dry run, recovery point, one transaction, idempotent, versioned. It writes only module materials
onto modules that already exist, and never touches lecture content, glossary bookmarks, progress or notes.

### 4. Application changes

- **Module page** (`/module?module=…`): the module's materials in the reader style, followed by its lecture guide
  with each lecture's status. It is reachable from the Library (module title) and from each lecture ("Module
  overview").
- **Exports:** Module .md and Module PDF start with the module materials, then the lectures. The course document
  includes each module's materials before its lectures. The Module ZIP includes the module's examples.
- **Library:** each module shows its own status ("module materials written / not written") beside the lecture count,
  so a module is never shown as complete only because its lectures are.
- **Audit:** module content gets the four statuses from the module standard. A module is COMPLETE only when its own
  materials are complete and every lecture is complete.

### 5. Quality rules (validator and tests)

All 12 sections in Malay and English. Glossary links resolve. Module examples are verified like lecture examples and
are not duplicates of any lecture example. There is a minimum depth per section. Every written module passes the same
end-to-end checks as lectures (page, PDF, Markdown).

## Implementation roadmap

| Phase | Work | Content written? | Needs |
|---|---|---|---|
| **M-1 Feature** | Module standard, types (`Module.sections`), package format, validator, installer, module page, exports, Library status, audit update, unit and e2e tests | **No.** The page honestly shows "Module materials not written yet" | your approval of the standard and storage |
| **M-2 Written courses first** | Module materials for the 32 modules whose lectures are written (LUA101–LUA104, LUAU101–LUAU104) | Yes, 32 modules | M-1; your approval to start |
| **M-3 With every new course** | From then on, each new course batch includes its 4 module materials with its 12 lectures, so no module ships without materials | Yes, alongside lectures | the content roadmap you approve (Lua S2, Luau S2, Python, …) |
| **M-4 Other disciplines** | Module standard profiles for maths and design, when those faculties get programmes | design first | curriculum design for F02–F07 |

**Workload estimate.** A module overview of this standard is about 1,500–2,000 words in both languages, plus 2–3
verified examples:

- **32 modules for the written courses:** about 50,000–65,000 words and 64–96 examples.
- **All 328 modules:** about 0.5–0.65 million words and 650–1,000 examples, on top of the 887 lectures still to write.

**Dependencies:**
- M-1 must come before any module content.
- The 4 LUAU101 modules would inherit the Roblox NEEDS VERIFICATION status if their examples use Roblox APIs.
- Python modules need the Python verifier, like Python lectures.
